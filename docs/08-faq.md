# 08 · 排错与常见问题

## 采集相关

### Q1：运行记录显示"已完成"，但新岗位 0 条，是不是坏了？

不是。看 note：

```
猎聘入库18条/领英入库9条/重复126个/清理重复0条/打分27条
```

`重复 126` 说明采到的岗位几乎都在库里了。同一批关键词每天搜两次，重复率 80%+ 是正常的——岗位市场没那么快换血。

只有当 `重复` 也很小、`入库` 也是 0 时，才是真的异常。

### Q2：同一岗位在清单里出现好几次

1. 先看是不是**名字略有差异**（"招聘SAP BPC顾问" vs "SAP BPC 顾问"）—— 去重规则会把它们合并
2. 若确实重复，点应用里「🧹 一键去重」，或执行 `scripts/dedupe.sql` 第 3 段
3. 若是每天新增的重复，检查采集任务的第 3 步是否按「岗位实体」判重（而不是按链接）

### Q3：为什么已经投递过的岗位又出现在"最新岗位清单"里？

说明查重没覆盖全状态。检查采集 prompt 的查询是否带了 `status` 过滤——**必须不带**：

```sql
-- ✅ 正确
SELECT id, company, position, source_url, status FROM jobs WHERE owner_id='<uid>' LIMIT 2000;
-- ❌ 错误（会漏掉已投递/已拒绝的岗位，导致重复入库）
SELECT ... FROM jobs WHERE owner_id='<uid>' AND status='待确认';
```

### Q4：采集记录里出现了 9:20 / 15:38 这种非整点记录

机器休眠后，"本机应用闹钟"会把错过的定时任务补跑。项目已内置两道防御：

1. **防重复补跑守卫**：先清 >2h 的僵尸 `processing`，再查 90 分钟内是否已有 `processing`，有则本轮静默退出
2. **看门狗**：每小时检查，>2h 仍 `processing` 直接标失败

如果你仍看到大量补跑，检查是否同时存在多个采集任务配置。

### Q5：手动点了「⚡ 通知 Agent 立即采集」，一直没反应

- 请求进的是 `agent_tasks(type='collect_now', status='pending')`
- 由**每小时**检查点任务消费，所以最长等 1 小时（平均 30 分钟）
- 若超过 2 小时还是 `pending`：检查每小时任务是否 ACTIVE

### Q6：两个手动请求都点了，会跑两轮吗？

不会。第二个会被标 `merged`（已合并），只跑一轮。这是设计行为。

## 领英相关

### Q7：一直是"失败原因：领英重定向linkedin.cn"

按顺序查（详见 [06-network.md](06-network.md)）：

1. `curl -s https://www.cloudflare.com/cdn-cgi/trace` 看 `loc` 是不是 `CN`
2. 切换节点后**出口 IP 是否变化** —— 不变就说明代理没接管（查 Fake-IP 与 TUN 是否配对）
3. 分流规则是否把 `linkedin.com` 走了直连
4. 出口是不是亚太 IPv6 段（被判 CN）

### Q8：代理明明是开的、节点是美国，为什么出口还是本机 IP？

最常见的三种原因：

| 原因 | 判据 | 修法 |
|---|---|---|
| Fake-IP 开着，TUN 关着 | 切任何节点出口都不变 | 开 TUN（或关 Fake-IP） |
| 内核卡死（数据面与配置面不一致） | 客户端显示已连接，配置正确，但流量不进隧道 | 重启客户端内核/服务，必要时重启电脑 |
| 客户端静默 fallback 直连 | 内核测节点延迟失败，但流量"还能通" | 换成能测通延迟的节点 |

> 排查顺序建议：先看**出口 IP 有没有变**，再看**节点延迟能不能测通**，最后才怀疑节点质量。多数时候问题在本地链路而不是节点。

### Q9：领英能打开但采集到的卡片很少 / 是空的

- 页面可能是懒加载未渲染 → 加大等待（6-8 秒）后重试一次
- 可能是登录态失效的软墙 → 提示用户手动打开 Edge 确认已登录
- 可能是页面结构改版 → 记录 `领英卡片解析为空`，不要猜数据

### Q10：能不能不登录抓领英？

不建议。未登录状态领英会频繁弹 authwall，重定向概率高，且抓到的列表不完整。本项目复用**用户自己的浏览器登录态**，不索取账号密码。

## 数据与界面

### Q11：对话卡住、发送按钮变灰

历史 bug，原因是流式请求无超时。现已改为：

- `llmJSON` 带 120 秒超时
- 请求期间禁用输入框并显示「AI 正在思考」
- `JSON.parse` 失败重试 1 次

若你复刻时又遇到，检查是否用了裸 `fetch` 而没加超时。

### Q12：仪表盘数字和数据库不一致

刷新时机是「数据写入后 +40 分钟」（08:40 / 10:00 / 18:40 / 20:00），外加切回页面即时同步。若你刚手动改了数据，点「立即刷新」。

### Q13：为什么不用每 20 分钟自动刷新？

数据每天只写 4 次（2 次采集 + 2 次反馈同步），20 分钟轮询 90% 是空转。改为"跟写入事件对齐"后体验不变、请求少 90%。

### Q14：匹配度为什么普遍不高（50-60 分）？

正常。打分纪律要求"证据不足按保守中间分"，且硬冲突直接压到 50 以下。这个分数的用途是**排序与筛选**，不是"我有多优秀"。

## 复刻相关

### Q15：自建后 4 张表建好了，但前端读不到数据（返回空数组）

依次检查：

1. `GRANT` 是否执行（漏了会得到 `42501`，看起来像 RLS 策略失效）
2. RLS 策略是否是 `owner_id = auth.uid()`
3. 插入时 `owner_id` 是否真的等于当前登录用户（`auth.uid()` 默认值是否生效）
4. `agent_tasks.owner_id` 是不是 **text** 而不是 uuid

### Q16：定时任务跑起来但报 `column ... does not exist`

任务 prompt 里引用的字段名必须与 `scripts/schema.sql` 完全一致。已知易错：

- `keywords_en`（不是 `keywordsEn`）
- `match_score` / `match_reason`（不是 `score` / `reason`）
- `agent_tasks.note`（不是 `message`）

### Q17：能不能换成别的数据库 / 自建后端？

可以，但要自己实现三件事：用户认证（含 `auth.uid()` 等价物）、行级隔离、免密钥 LLM 代理。前端只依赖 `cloud.*` 这几个 API，替换 SDK 即可。
