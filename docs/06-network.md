# 06 · 网络边界：领英岗位搜索的硬性前置条件

> 本文回答一个问题：**在什么条件下，才允许 Agent 自动执行领英岗位搜索？**
>
> 结论先行：必须同时满足 **①出口 IP 不被判定为中国大陆** 和 **②`linkedin.com/jobs/search` 跟随站内跳转后仍可访问（200；或 401/403 表示需登录）**，且最终不落 `linkedin.cn`。任何一条不满足 → **跳过领英、如实记录原因，禁止降级为直连抓取**。

---

## 为什么领英需要单独的边界

领英对来自中国大陆的 IP 会做一次**国家/地区重定向**：

```
中国大陆 IP 请求 https://www.linkedin.com/jobs/search/?keywords=...
   → HTTP 302  Location: https://www.linkedin.cn/incareer/jobs/search/?keywords=...
   → linkedin.cn 是中国区站点，未登录/受限时返回 451 或空壳页
```

后果有两层：

1. **拿不到数据** —— 抓到的不是真实岗位列表，是空页或中国区内容
2. **更危险的是"看起来成功了"** —— 如果没有做状态码检查，采集程序会把空结果当成"今天没有新岗位"，用户看到"已完成 0 条"，误以为是市场冷清，实际上是网络问题

所以本项目把它做成了**显式门禁**：不满足就跳过并记录原因，不猜、不兜。

---

## 硬性前置条件（必须同时满足）

### 条件 1 · 出口 IP 的地理判定不是中国大陆

领英根据**出口 IP 的地理库**判断用户所在地区，与你在哪里、账号注册地都无关。

- 可用：US、SG、JP、HK 等（推荐 US，领英美国站数据最全）
- 不可用：任何 `loc=CN` 的出口，包括"看起来是海外节点但 IP 段被登记为中国"的情况

### 条件 2 · 代理必须真正接管流量

这是本项目排查中花时间最多的一类问题。典型症状：**代理界面显示"已连接、美国节点"，但实际出口还是本机 IP。**

| 成因 | 表现 | 判据 |
|---|---|---|
| 只开了"系统代理"注册表，内核未接管 | 浏览器似乎能翻，命令行全直连 | 走代理端口访问 `cloudflare.com/cdn-cgi/trace`，出口 = 本机 IP |
| **Fake-IP 开着但 TUN 关着** | DNS 解析出 `198.18.x.x` 假地址，无人接管，全部漏回直连 | 同上；且切换任何节点出口都不变 |
| 分流规则把 `linkedin.com` 走 DIRECT | 其他外站正常，唯独领英 302 | 领英 302 但 `google` 200 |
| 节点是死的，客户端静默回落直连 | 换节点无感，出口恒为本机 IP | 内核测节点延迟失败，但流量"还能通" |

**本项目实际踩过的完整案例**（记录在此，便于你对照）：

```
现象：代理客户端显示「已连接 · 美国节点 · 全局模式」，但
      - 走代理访问 cloudflare trace → 出口 = 本机中国电信 IPv6（240e:...）
      - linkedin.com/jobs/search → 302 → linkedin.cn
      - 依次切换 US / HK / SG / JP 共 8 个节点，出口 IP 完全一致（都是本机地址）
诊断：Fake-IP = true 且 TUN = false。假 IP 无人接管 → 流量漏回直连。
      （期间还排除了：节点失效、DNS 劫持、安全软件拦截、运营商问题 —— 全部不是）
修复：开启 TUN 模式 → 出口变为 23.148.156.133（US Houston），
      linkedin.com/jobs/search 返回 200，采集恢复。
```

### 条件 3 · 出口 IP 的地址段本身不能"被判 CN"

有些海外节点用的是亚太段 IPv6（例如 `240e::/20`、`2401:ce20::/32` 这类中国电信/亚太注册段），地理库会把它们判成 CN，即使节点物理位置在美国。

- 优先使用 **IPv4 出口**
- 若出口是 IPv6，必须实测 `loc` 不是 CN
- 同一节点的 IPv4 与 IPv6 出口可能是**不同国家判定**（本项目的案例里，HTTP 走 IPv4 判 US，HTTPS 走 IPv6 判 CN）

### 条件 4 · 浏览器与命令行必须同一出口

采集用的是**你本人的 Edge**（复用登录态），验证却常用命令行。两者若走的不是同一条链路（例如浏览器走了代理、curl 走了直连），就会出现"脚本说通、采集却失败"。

- 最省心的做法：开 **TUN 全局**，让所有进程都被接管
- 用系统代理模式时，必须确认浏览器进程确实读到了代理设置

## 运行前自检（两条硬断言）

```bash
bash scripts/check-network.sh
```

脚本做的事：

| 断言 | 命令 | 通过 |
|---|---|---|
| 1（硬） | `curl -s https://www.cloudflare.com/cdn-cgi/trace` | `loc` ≠ `CN` |
| 2（硬） | `curl -s -o /dev/null -w '%{http_code}' 'https://www.linkedin.com/jobs/search/?keywords=AI%20Product%20Manager'` | `200` |
| 3（辅助） | 对比出口 IP 与本机直连 IP | **不参与门禁** —— TUN 全局模式下令牌两者相同是正常的 |

> 为什么第三条不能做门禁：TUN 模式下所有流量都进隧道，"直连测出来的 IP"其实也是代理出口，两者必然相同。早期版本用这条做门禁，结果在**正常工作**的环境上报错。判定链路是否生效，看断言 1、2 的结果就够了。

## 失败原因对照表（写进 `agent_tasks.note` 用）

| 观测 | 归因 | 记录原因（≤40 字） | 处置 |
|---|---|---|---|
| `302 → linkedin.cn` | 出口被判 CN，或 linkedin 被分流直连 | `领英重定向linkedin.cn` | 修网络后重跑，本轮跳过 |
| `451` | 区域限制 | `领英451区域限制` | 同上 |
| `999` | 领英风控（请求特征异常） | `领英999风控` | 降低频率；本轮跳过 |
| `200` + authwall/登录页 | 浏览器登录态失效 | `领英登录态失效需人工登录` | 提示用户手动登录 Edge |
| `000` / 超时 | 代理不通 | `领英请求超时` | 检查代理 |
| `200` 但读不到卡片 | 页面结构变更 / 懒加载未渲染 | `领英卡片解析为空` | 跳过并提示可能改版，不猜数据 |

## 采集频率与行为约束（自我限速）

| 项 | 上限 | 原因 |
|---|---|---|
| 每轮关键词数 | 3 | 覆盖主要方向即可 |
| 每关键词页数 | 1 | 不翻页，避免高频特征 |
| 每页条数 | 25 | 首页可见卡片量 |
| 词间隔 | 30-60 秒随机 | 模拟人工节奏 |
| 每日轮次 | 2 次定时 + 少量手动 | 手动触发有合并机制，避免叠加 |
| 单轮入库 | 120 条 | 防御性上限 |

**明确禁止**：

- ❌ 翻页、无限滚动
- ❌ 点开职位详情页
- ❌ 点击 Easy Apply / 投递
- ❌ 绕过验证码、登录墙、人机验证
- ❌ 用打码服务
- ❌ 在检测到重定向后"改成直连继续抓"（拿到的是中国区内容，等于脏数据）

## 猎聘为什么没有这个门禁

猎聘是国内站点，从中国大陆直连即可，不需要代理；反而**走代理更慢、更容易触发风控**。所以：

- 猎聘：本机直连采集，无前置条件
- 领英：独立门禁，不满足就跳过

两者互不影响 —— 领英挂了，猎聘与打分照常跑。这是设计意图，不是失败。

## 一页速查

```
跑领英前，先问四个问题：
1. 出口 IP 的 loc 是不是 CN？          → 是 → 停
2. linkedin.com/jobs/search 是不是 200？ → 不是 → 停
3. 刚才切节点，出口 IP 变了吗？          → 没变 → 代理没接管（查 Fake-IP / TUN 配对）
4. 出口是 IPv6 吗？段是不是亚太/中国电信？→ 是 → 换美国 IPv4 出口
```
