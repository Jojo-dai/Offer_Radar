# 06 · 网络边界：领英岗位采集能用什么判据决定「跑 / 不跑」

> 本文回答一个问题：**在什么条件下，才允许 Agent 自动执行领英岗位采集？**
>
> 结论先行（2026-11-06 修订）：**唯一判据是「接口是否真的返回岗位卡片」，不是「出口 IP 属于哪个国家」。**
> 用 `jobs-guest` 接口试一次，返回 ≥1 条卡片 → 放行；返回 `302 → linkedin.cn` / `429` / `451` / 0 条卡片 → 跳过领英并如实记录原因。
> **出口 IP 只作为诊断提示打印，不参与门禁。**

---

## 为什么判据从「IP」改成了「接口」

旧版本文档写的是：出口 IP 必须不是中国大陆，且 `linkedin.com/jobs/search` 返回 200，否则整段跳过领英。

这个判据在**理论**上说得通（领英对中国大陆 IP 会 302 到 `linkedin.cn`），在**实际**上却造成了整天的数据空洞：

```
2026-11-06 的翻车现场
09:13 补跑：出口 116.237.170.135（上海电信，loc=CN）→ 判 CN → 跳过领英 → 只采猎聘 37 条
18:09 定时：出口仍是同一 IP → 判 CN → 跳过领英 → 只采猎聘 43 条
当天领英入库：0 条
22:40 复测：代理恢复（US IPv6），jobs-guest 返回 200 —— 说明接口一直是好的
```

问题不在代理，在**判据**：

| 旧判据 | 它真正测的是什么 | 后果 |
|---|---|---|
| `loc ≠ CN` | 出口 IP 在某个地理库里的登记国 | 代理一抖动（节点切换、TUN 掉线、IPv6 出口被判 CN）就整天误判 |
| `jobs/search` 返回 200 | 那个**网页**能不能打开 | 网页 200 不代表接口能用；接口 200 也不代表网页 200 |
| 二者取与 | 两个间接代理指标 | 任一为假就整段放弃，哪怕真实能力还在 |

**接口本身能不能返回数据，才是唯一和结果相关的事实。** 于是判据改成直接问接口。

> 这个改动不是「放宽门禁」，而是把门禁对准它本来要防的东西：旧判据要防的是「抓到 `linkedin.cn` 的中国区空壳页」，那么**直接检查有没有抓到卡片**，比检查 IP 更贴近目标，也更不容易误伤。

## 现在的门禁（唯一实现：脚本内置）

```bash
bash job-apply-agent/scripts/check-network.sh     # 自检，人工排查用
python job-apply-agent/scripts/collect-linkedin-guest.py --keywords "..." --pages 5   # 采集，门禁已内置
```

脚本按顺序做三件事，**只有前两件决定能否采**：

| 步骤 | 内容 | 是否门禁 |
|---|---|---|
| 1（硬） | 请求 `jobs-guest` 接口，统计返回的岗位卡片数。**≥1 条 → PASS** | ✅ 唯一正向断言 |
| 2（硬） | 若发生 `302 → linkedin.cn`、或状态码为 `429 / 451 / 999`、或卡片数 0 → FAIL，退出码 2 | ✅ 反向判据 |
| 3（提示） | 打印出口 IP 与 `loc`，**仅供参考，不影响结果** | ❌ 不参与判定 |

探测用**前两个关键词**各试一次，避免「某个词本来就搜不到岗位」被误当成接口不可用：

```
GATE PASS [SAP BPC] http=200 cards=10
GATE RETRY [AI Product Manager] http=200 cards=0     ← 换下一个词再试
SKIP linkedin: 全部探针 0 条卡片                      ← 才判失败，退出码 2
```

## 为什么 IP 仍然值得看一眼（诊断，不是门禁）

门禁不看 IP，但**出问题时 IP 是最快的定位线索**。以下现象仍然存在，只是它们现在表现为「接口失败」，而不是「IP 是 CN 所以不试」：

### 领英对中国大陆 IP 的行为

```
中国大陆 IP 请求 https://www.linkedin.com/jobs-guest/jobs/api/seeMoreJobPostings/search?...
   → HTTP 302  Location: https://www.linkedin.cn/incareer/jobs/search?...
   → linkedin.cn 是中国区站点，未登录/受限时返回 451 或空壳页
```

后果有两层：

1. **拿不到数据** —— 抓到的是空页或中国区内容
2. **更危险的是「看起来成功了」** —— 不做校验的话，采集程序会把空结果当成「今天没有新岗位」

所以门禁必须存在，只是判据换成「卡片数」。

### 代理没真正接管流量的典型症状

| 成因 | 表现 | 判据 |
|---|---|---|
| 只开了「系统代理」注册表，内核未接管 | 浏览器似乎能翻，命令行全直连 | 接口 302 到 `linkedin.cn`，但 `google` 正常 |
| **Fake-IP 开着但 TUN 关着** | DNS 解析出 `198.18.x.x` 假地址，无人接管，全部漏回直连 | 切换任何节点，接口都 302 |
| 分流规则把 `linkedin.com` 走 DIRECT | 其他外站正常，唯独领英挂 | 同上 |
| 节点失效，客户端静默回落直连 | 换节点无感，出口恒为本机 IP | 内核测节点延迟失败，但流量「还能通」 |

**本项目实际踩过的完整案例**（保留在此，便于对照）：

```
现象：代理客户端显示「已连接 · 美国节点 · 全局模式」，但
      - 走代理访问 cloudflare trace → 出口 = 本机中国电信 IPv6（240e:...）
      - linkedin.com/jobs/search → 302 → linkedin.cn
      - 依次切换 US / HK / SG / JP 共 8 个节点，出口 IP 完全一致（都是本机地址）
诊断：Fake-IP = true 且 TUN = false。假 IP 无人接管 → 流量漏回直连。
修复：开启 TUN 模式 → 出口变为 23.148.156.133（US Houston），接口恢复 200。
```

### 出口是 IPv6 亚太段时

有些海外节点用亚太段 IPv6（如 `240e::/20`、`2401:ce20::/32`），地理库会判成 CN。此时**接口可能仍然可用** —— 这正是旧判据误伤的典型场景。若接口确实失败，优先切 IPv4 出口再试。

## 失败原因对照表（写进 `agent_tasks.note` 用）

| 观测 | 归因 | 记录原因（≤40 字） | 处置 |
|---|---|---|---|
| `302 → linkedin.cn` | 代理未接管，或节点被判 CN | `领英重定向linkedin.cn` | 修网络后下轮再试；本轮跳过 |
| `451` | 区域限制 | `领英451区域限制` | 同上 |
| `429` | 触发限速 | `领英429限速` | 本轮立即停止，不重试；下一轮自然恢复 |
| `999` | 领英风控（请求特征异常） | `领英999风控` | 降低频率；本轮跳过 |
| `000` / 超时 | 网络不通 | `领英请求超时` | 检查代理 |
| `200` 但 0 条卡片（换 2 个词仍 0） | 页面改版 / 解析失效 | `领英卡片解析为空` | 走 Edge 回退路径（见 05），并提示可能改版 |

## 采集频率与行为约束（自我限速）

| 项 | 上限 | 原因 |
|---|---|---|
| 每轮关键词数 | 4 | 覆盖 4 个方向，15 词池 2 天轮完一遍 |
| 每关键词页数 | 5 | 实测 `start=40` 仍有结果；超过 5 页收益趋零 |
| 每页条数 | 10 | 接口单页固定 10 条 |
| 页间隔 / 词间隔 | 3 秒 / 4 秒 | 直连接口，无需模拟人工滑动 |
| 每日轮次 | 2 次定时 + 少量手动 | 手动触发有合并机制，避免叠加 |
| 单轮入库上限 | 200 条 | 防御性上限 |

**明确禁止**：

- ❌ 点开职位详情页
- ❌ 点击 Easy Apply / 投递
- ❌ 绕过验证码、登录墙、人机验证；❌ 用打码服务
- ❌ **抓取 `linkedin.cn` 的内容**（那是中国区站点，不是真实海外岗位数据）
- ❌ 在 `429` 后立刻重试（要等下轮）

> 与旧版的差异：旧版禁止「直连抓取」，因为当时直连等于抓 `linkedin.cn`。现在直连抓的是**领英官方访客接口本身**（`jobs-guest`），它返回的就是真实岗位卡片，**这正是当前的主路径**。禁止对象从「直连」精确化为「抓 `linkedin.cn`」。

---

## 猎聘为什么没有这个门禁

猎聘是国内站点，从中国大陆直连即可，不需要代理；反而**走代理更慢、更容易触发风控**。所以：

- 猎聘：本机直连采集，无前置条件
- 领英：接口实测门禁，不满足就跳过

两者互不影响 —— 领英挂了，猎聘与打分照常跑。这是设计意图，不是失败。

## 一页速查

```
领英采集前，只问一个问题：
  用 jobs-guest 试两个词，能返回卡片吗？
    能 → 采（不用管 IP 是什么）
    不能 → 看是哪一种：
        302 → linkedin.cn   → 代理没接管（查 Fake-IP / TUN 配对、分流规则）
        429                 → 限速了，本轮别采，下轮再来
        451 / 999           → 区域限制 / 风控，本轮跳过
        200 但 0 条          → 可能改版，走 Edge 回退路径
```
